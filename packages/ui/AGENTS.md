# Инструкции для `@daevox/ui`

## Назначение пакета

`@daevox/ui` — React 19 UI-пакет приложения daevox. Он содержит layout, страницы чата,
feature-модули, UI units без дополнительной логики, связанной с Effector stores,
Effector stores, API-адаптер и стили.

Основные области:

- `src/app.tsx` — корневой UI-компонент;
- `src/layout/` и `src/pages/` — каркас и страницы приложения;
- `src/features/` — связанные с фичами компоненты и stores;
- `src/units/` — UI-компоненты без дополнительной логики, связанной с Effector stores;
- `src/api.ts` — API-адаптер UI;
- `*.module.css` — локальные стили компонентов;
- `theme.css` и `index.css` — глобальные design tokens, шрифты и базовые стили.

## Структура и импорты

- Новые компоненты размещать рядом с их стилями, тестами и Storybook story.
- Для публичных компонентов и feature-модулей поддерживать локальный `index.ts` или `index.tsx`, если это соответствует существующей структуре каталога.
- Сохранять ESM-совместимые относительные импорты с расширением `.js` в TypeScript/TSX-файлах.
- Не импортировать внутренние детали другой feature напрямую, если для них уже есть публичный export.
- Сохранять существующую организацию `features`, `layout`, `pages` и `units`; не переносить код между слоями без необходимости.

## React и TypeScript

- Использовать функциональные React-компоненты и hooks, следуя существующим паттернам проекта.
- Для props переиспользуемых нативных элементов предпочитать типы React вроде `ComponentProps<"button">` и сохранять поддержку стандартных props, если это не противоречит API компонента.
- Для условных классов использовать существующий подход с `classnames` или массивами классов; не дублировать сложную логику классов в JSX.
- Для локального состояния использовать React state, а состояние feature и асинхронные эффекты держать в соответствующем Effector store, если оно используется несколькими компонентами или связано с API.
- Не дублировать API-вызовы в компонентах: использовать адаптер из `src/api.ts` и существующие stores.
- Не менять публичные типы компонентов и контракты без необходимости; при изменении поведения обновлять связанные тесты и stories.
- Сохранять локальный стиль форматирования файла и не делать массовое форматирование несвязанных компонентов.

## Стили и дизайн

- Для стилей компонентов использовать CSS Modules (`*.module.css`), а не новые глобальные селекторы.
- Цвета, границы, фокус, поверхности и другие общие значения брать из CSS-переменных `theme.css`, когда подходящий token уже существует.
- Глобальные изменения вносить только в `theme.css` или `index.css` и проверять их влияние на light/dark темы.
- Учитывать существующие шрифты, spacing, radius и визуальные паттерны; не вводить новую систему дизайна для одного компонента.
- При изменении UI проверять состояния loading, error, empty, disabled и переполнение контента, если они применимы.

## Доступность и поведение

- Использовать семантические HTML-элементы и нативные controls, когда они подходят.
- Обеспечивать доступные labels, роли, состояния, фокус и управление с клавиатуры для интерактивных элементов.
- Не использовать только цвет для передачи состояния; сохранять текстовую или семантическую альтернативу.
- При изменении интерактивного поведения добавлять проверки для keyboard/disabled/error-состояний и соответствующих ARIA-атрибутов.
- Учитывать, что UI запускается как в Electron-приложении, так и изолированно в Storybook.

## Тесты и Storybook

- Тесты размещать рядом с исходным файлом: `*.test.ts`, `*.test.tsx`.
- Для компонентных тестов использовать `src/units/test-utils.tsx`, чтобы сохранить единый lifecycle React roots и cleanup.
- В тестах проверять пользовательское поведение и доступный DOM, а не внутреннюю реализацию компонента.
- Для units добавлять stories рядом с компонентом (`*.stories.tsx`), если у него есть отдельные варианты, состояния или сценарии, которые полезно проверять в Storybook; переиспользуемость не является обязательным критерием.
- В stories использовать `Meta`/`StoryObj` из `@storybook/react-vite`; для интерактивных callbacks использовать существующий подход с `fn` из `storybook/test`.
- При изменении компонента, который уже имеет story, обновлять story вместе с компонентом.
- Не удалять тесты только для упрощения покрытия; сначала исправлять контракт или добавлять явное исключение с объяснением.
- В `vitest.config.ts` для coverage настроены пороги 100% по statements, branches, functions и lines для перечисленных UI-компонентов. При изменении этих файлов сохранять пороги и дополнять тесты.

## Команды проверки

Из корня репозитория:

```bash
npm --workspace @daevox/ui run build
npm --workspace @daevox/ui test
```

Для изменений в coverage-критичных компонентах:

```bash
npm --workspace @daevox/ui run coverage
```

Для изменений в stories, Storybook-конфигурации или глобальных стилях:

```bash
npm --workspace @daevox/ui run build-storybook
```

При изменениях, затрагивающих контракты или интеграцию с другими пакетами, дополнительно запускать проверки, указанные в корневом `AGENTS.md`.

В итоговом сообщении указывать изменённые UI-области и выполненные проверки. Если проверку нельзя запустить, указывать причину.
